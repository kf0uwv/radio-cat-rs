# ADR 0024 — `cat-ft8`: FT8 from the published protocol, with a `no_std` core

Status: Accepted (2026-10-26)

## Context

FT8 is the most used digital mode on the HF bands. Applications built on
this library want to send it, and later to decode it, beside the CAT
control, audio and Morse support they already get here.

It belongs in this repository for the same reason `cat-morse` does
([ADR 0021](0021-cat-morse.md)): almost all of it is radio-independent.
The message formats, error correction, tones and waveform are the same for
every radio, so putting them in one application would mean every other
application copies them. Like `cat-morse`, the crate keys nothing and
opens no sound card; it turns text into samples (and, later, samples into
text).

The reference implementation, WSJT-X, is licensed under the GPLv3. This
library is Apache-2.0. The protocol itself is published: S. Franke, B.
Somerville and J. Taylor, "The FT4 and FT8 Communication Protocols", QEX,
July/August 2020. `ft8_lib` (Kārlis Goba, MIT) is an independent
implementation that interoperates with WSJT-X.

FT8 decoding is CPU-heavy. A `no_std`, allocation-free core lets
applications run it on small embedded targets as well as on hosts.

## Decision

**A new workspace crate, `cat-ft8`, implements FT8 from the published
protocol description.** This first release is the transmit half: message
packing (and unpacking, which tests and the future decoder need), CRC-14,
LDPC (174,91), tone mapping and GFSK waveform synthesis. Decoding follows
in later releases in the same crate, each with its own plan and an
amendment to this ADR.

### Scope rules

1. **No radio.** No keying, no CAT and no dependency on `cat-framework`,
   any `cat-transport-*` or any radio crate.
2. **No device audio.** It writes `f32` PCM at 12 000 Hz into the caller's
   buffers (the `std` feature can also write a WAV file). Playback belongs
   to the application.
3. **`no_std` core, no dependencies.** The crate is `#![no_std]` in every
   build and has no dependencies at all. The core allocates nothing
   (fixed-size arrays and caller-provided buffers) and starts no threads.
   All floating-point work is `f32` `+ − ×`: there is no `f64` and no
   transcendental function at run time, because the pulse shape and sine
   are tables in static data. CI proves this on every change for
   `thumbv8m.main-none-eabihf`: the library builds and lints for that
   target, and `cat-ft8/embedded-check` links a `#![no_main]` program
   with **no allocator** and fails on any unresolved symbol or any `f64`
   soft-float helper (`__aeabi_d*`, `__*df*`) in the image. The program
   calls `encode` (pack, CRC, LDPC, tones) and `unpack`, and every public
   entry point that does floating-point work — `Placement::slot`,
   `synthesize` (at a negative start), `Synth::new`, `fill`, `mix`, `skip`,
   `fill_phase`, `sin_turns` and `cos_turns` — because only reachable code
   is linked and so checked. The remaining public functions are
   integer-only. A new floating-point entry point must be added to it. Injecting one `f64`
   operation into `synthesize` makes the check fail.
4. **Features.** `std` (default) adds `std::error::Error`, WAV output and
   the `cat-ft8-encode` binary. `profile` (default-off) builds the
   `encode_bench` example, which reports CPU time per stage, the memory
   account and a heap-allocation count; it does not change the library.
   CI builds both, tests the host build without `std`, and builds the docs
   with warnings as errors in both configurations (ADR 0014 §5).
5. **No unsafe code** in the library (`#![forbid(unsafe_code)]`).
6. **Errors** are one hand-written `Error` enum, `#[non_exhaustive]` so
   the decoder can add variants. `thiserror` is not used: the workspace's
   `thiserror` 1.x needs `std`. `thiserror` 2 supports `no_std` and was
   considered; a dependency for one `Display` impl was not worth it.

### Provenance

- **Implemented from the QEX 2020 paper** (Tables 1–3 and 7, §3–5,
  Appendix A). WSJT-X source code is not read, copied, ported or
  translated.
- **WSJT-X tools are black-box test oracles only.** The encoder vectors in
  `cat-ft8/tests/data/` were generated from WSJT-X 3.0.0-rc1 `ft8sim`
  output (its printed payload bits, channel symbols and its own unpack of
  each message), and WSJT-X's `jt9` was used to confirm by hand that the
  synthesized audio decodes. Neither is linked, shipped or needed to build
  or test this crate. Where the paper is silent or WSJT-X differs from it,
  this crate follows what the oracle does (listed below), so both put the
  same bits on the air.
- **`ft8_lib` (MIT) was consulted** — its CRC, message packing, encoder
  (LDPC encoding and tone mapping) and waveform code — and is credited in
  `cat-ft8/NOTICE`. Copied from it: the
  LDPC generator and parity-check matrices (the paper defines them by
  reference to files it does not print). Followed from it: the waveform's
  extension of the first and last tone beyond the transmission, which the
  paper does not specify. Taken from it: the callsign-hash multiplier
  (47 055 833 459) and the order of the 38-character callsign alphabet,
  which the paper defers to reference programs it does not print; the
  free-text alphabet the paper prints matches. The Rust for CRC, packing,
  LDPC encoding, tone mapping and synthesis was written from the paper; no
  `ft8_lib` function was translated. The tables and the
  hash multiplier originate in WSJT-X; they are interoperability constants
  of the protocol and are used here as facts.

### The determinism promise

Packing, CRC, LDPC and tone mapping are integer-only. The waveform uses
only IEEE-754 `f32` `+ − ×` (Rust never fuses them into FMA), a 32-bit
fixed-point phase accumulator, and two tables in static data: the GFSK
pulse (QEX eq. 3) and a quarter-wave sine, read by the top phase bits and
linearly interpolated with an integer-derived fraction. Both tables are
generated with `libm` and checked bit-for-bit by a test, so `libm` is a
dev-dependency only (pinned exactly). Given IEEE-754 binary32 arithmetic
with round-to-nearest — every target with SSE2 or a hardware
single-precision FPU, and soft-float targets, but not x87-only targets
such as i586, which round through extended precision — **the same
symbols, frequency, amplitude and position give bit-identical samples on
every platform**, whether rendered in one call or in blocks. (`mix` into a
zeroed buffer equals `fill` except in the sign of zero.) Tests pin FNV-1a hashes of synthesized waveforms
and full slots; CI runs them on Linux and Windows. A deliberate change to
the waveform changes the hashes in the same commit.

### Recorded design choices

- **Message types.** Packed and unpacked: 0.0 free text, 0.1 DXpedition,
  0.5 telemetry, 1 standard, 2 EU VHF `/P`, 4 nonstandard call, 5 EU VHF
  contest. Returned as `Error::Unsupported(type)`: 0.3/0.4 ARRL Field Day
  and 3 ARRL RTTY Roundup, which need the ARRL/RAC section and
  state/province tables whose order is part of the protocol; they are left
  for a later release rather than guessed. Their text shapes are recognised
  so they are reported as unsupported instead of being sent as free text.
  The unassigned types (0.2, 0.6, 0.7, 6, 7) unpack as
  `Error::InvalidPayload`, as do field values no message defines (for
  example a standard-call value `pack` never produces).
- **Text rules follow WSJT-X 3.0**, checked against `ft8sim`:
  - type 1/2 signal reports run from −50 to +50 dB (the paper says −30 to
    +99; WSJT-X carries −31…−50 in otherwise unused values and shows
    anything above +50 as `dd − 101`);
  - `RR73` is sent as the locator RR73 (g15 = 32 373), not the reserved
    value the paper lists; both unpack to `RR73`;
  - free text shorter than 13 characters is right-aligned (leading
    spaces);
  - any single word of 1–18 hexadecimal digits is telemetry (0.5);
  - in a type 4 `CQ` message the ignored `h12` field holds the hash of the
    call itself;
  - a hashed `<call>` goes in a type 1 message beside a standard call
    without suffix, or beside another hashed call when neither contains
    `/`; beside a nonstandard or `/R`/`/P` call, or with a compound (`/`)
    call in both brackets, the message is type 4;
  - type 5: both calls bracketed (12- and 22-bit hashes), report 52–59
    and serial 0–2047 written as six digits, a 6-character locator.
- **Where WSJT-X loses information, this crate refuses.** WSJT-X
  truncates free text to 13 characters, drops a report it cannot fit into
  type 4, drops the prefix of an unbracketed compound call (`PJ4/K1ABC
  W9XYZ` is sent as `K1ABC W9XYZ`), wraps reports above +50, clamps a type
  5 serial above 2047, and drops the `+` of `+1` (sending telemetry 1).
  For the first five, `pack` returns an error; `+1` is sent as free text.
  Some compound-call shapes WSJT-X cannot pack still fit as free text and
  are sent that way, losslessly. Nonstandard calls are never hashed
  implicitly: the text must bracket one call.
- **Callsign hashes** are resolved through a `CallHashes` trait;
  `CallTable<N>` is a fixed-capacity table that keeps the `N` most
  recently heard calls (re-hearing refreshes a call). Parsing has no side
  effects: a successful `pack` offers the message's full calls once (the
  text is the operator's own); a failed one offers nothing. `unpack`
  remembers what WSJT-X 3.0 remembers when it decodes, checked black-box
  with `jt9`: only the sending station — the second call of a type 1/2
  message, the full call of a type 4 message when it is the sender, nothing
  from DXpedition or type 5 — exactly as written, so after `K1ABC/P` a hash
  of `K1ABC` alone does not resolve. It resolves every hash in the message
  first and remembers only after the whole payload has decoded. A miss shows `<...>`, as WSJT-X does. 10- and 12-bit hashes
  collide in practice; the protocol cannot tell such calls apart.
- **Unpacking writes to the hash table**, so a decoder that wants
  reproducible output must unpack its decodes in a fixed order on one
  thread, and only payloads that passed CRC and LDPC. The decoder's plan
  records how it does this.
- **CRC-14**: polynomial 0x6757, initial value zero, over the 77 payload
  bits zero-extended to 82 (QEX §3).
- **Waveform**: Gaussian-smoothed frequency pulse with BT = 2 (QEX eq. 3),
  tone spacing 6.25 Hz, 1920 samples per symbol at 12 kHz, three
  overlapping pulses per sample, a raised-cosine ramp over the first and
  last T/8 (20 ms, QEX §5), first and last tone extended beyond the
  transmission. A slot places the signal at 0.5 s + dt. `Synth` streams
  the waveform into caller blocks of any size (`fill`, `mix`), so a small
  target never needs the 607 KB waveform or 720 KB slot in memory, and
  exposes each sample's carrier phase and envelope (`fill_phase`) from the
  same generator. **The waveform API will grow** when the decoder needs a
  reference signal for subtracting decoded signals; transmit and
  subtraction will share this generator.

## Verification

- `cargo test -p cat-ft8`: per-stage unit tests (CRC; every LDPC basis
  codeword satisfies the parity checks and every single-bit flip breaks
  one; Costas positions and property; Gray map against QEX Table 3; the
  static tables against `libm`; sine accuracy; pulse normalisation,
  frequency, ramps; block rendering equal to one call; golden hashes);
  seeded property tests (round trips of every supported type; a random
  payload fuzz in which `unpack` never panics and, with the call table
  seeded with the calls behind each hash, every supported type — hashed
  types 1, 4, 5 and 0.1 included — repacks to the same bits or has a
  named non-canonical reason); and three black-box vector
  files. Every payload in them maps to `ft8sim`'s symbols; every supported
  message packs to `ft8sim`'s bits and unpacks to its text. Unsupported
  types, oracle failures and the documented deviations are counted, never
  skipped silently.
- `cat-ft8/embedded-check/check.sh`: the bare-metal link check above; with
  `--stack` it also prints per-function stack frames.
- Audio checked by hand with WSJT-X's `jt9` (not part of the test suite,
  which must not need WSJT-X).

## Consequences

- Applications get an FT8 transmit path with no GPL code in it, usable on
  hosts and microcontrollers alike, with no dependencies.
- The decoder will extend this crate under the same rules: `no_std` core,
  memory reserved up front by the caller, `f32`, no threads in the core.
- Field Day and RTTY Roundup messages need their lookup tables before they
  can be supported.
- Behaviour that follows WSJT-X rather than the paper is listed above, so
  a later WSJT-X change is a deliberate update to the vectors, not a
  surprise.

## Amendment (2026-10-26): single-pass decoder

Status: **Accepted (2026-10-26).** Memory, flash and stack figures were
measured on 2026-10-27 and replace the estimates; decode-rate and cost
evidence is under "Time budgets". The step plan is in
`planning/cat_ft8/task_plan.md` (Phase 2).

### Scope

A single-pass decoder in the same crate: slot framing, a block-fed
spectrogram, Costas sync search, single-symbol soft bits, LDPC belief
propagation, CRC check and unpacking, with frequency, time-offset and SNR
estimates. Later amendments cover subtraction and further passes,
multi-symbol block detection, ordered-statistics decoding, a-priori
decoding, decoding before the slot ends, and further single-pass
refinements (more rounds and candidates, early stopping of failing
candidates, a normalised sync threshold, per-bin noise normalisation,
window choice). Continuing past a codeword whose CRC fails was measured
(2026-10-27) and is not pursued: belief propagation continued past a
CRC-failing codeword never reached a different one. The first measured
result is expected near an external reference decoder's single-pass
level.

### Amendment to scope rule 3 (arithmetic)

Rule 3 is restated for the whole crate as follows.

- **Allowed at run time:** `f32` `+ − × ÷`, comparisons, conversions
  between `f32` and integers, integer arithmetic, and in-crate polynomial
  or rational approximations (of `log2` for log-magnitudes, and of `tanh`
  and `atanh` if belief propagation uses them), evaluated in a fixed order.
- **Not allowed at run time:** `f64`, `libm`, any platform
  transcendental function, and `sqrt`. None is needed: levels are taken
  from power (|X|²) through `log2`, so no magnitude square root is
  computed.
- **Tables:** the FFT twiddles, the window, the digit-reversal
  permutation and the level-to-power table (256 entries) are static
  data, generated with `libm` at development time and checked
  bit-for-bit by tests, like the waveform tables.

### Spectrogram geometry

- Row k is a 3 840-sample Hann window over samples [240 + 960k,
  240 + 960k + 3 840), for k = 0..184: two-fold oversampling in time (hop
  960, half a symbol) and in frequency (3.125 Hz bins). The 240-sample
  origin puts the symbol centres of a signal starting exactly at the
  nominal 0.5 s on the row grid.
- Every symbol centre has a row for dt ∈ [−0.40, +1.76] s. (The sample
  extent alone would allow [−0.48, +1.84] s; the row centres are what
  count.) The search covers dt ∈ [−2.5, +2.5] s. Symbols without a row
  are absent: they are not scored in sync, and their bits are erasures
  (LLR 0).
- A candidate needs at least two of its three Costas arrays inside the
  rows. Its score is the summed score of the n arrays present, multiplied
  by 6 / n (× 3 or × 2), so partial and full candidates compare exactly on
  one integer scale.
- **Band** means the base (tone 0) frequencies searched. The stored
  spectrum covers the band, the 43.75 Hz above its top, and one guard
  bin. The default band is 100–3100 Hz: 961 base bins and 976 stored
  bins.
- **Levels** are log-magnitudes from the in-crate `log2`, with a power
  floor so no subnormal value reaches it. They are stored as 8-bit (0.5 dB
  steps). A 16-bit form was measured with soft bits and belief
  propagation on synthetic slots and decoded no better (about +0.2 points
  of decode rate, within noise), so there is one configuration: levels
  are `u8` (an earlier sealed level trait was removed as unneeded).

- On the 256 KiB class the small configuration is the fit. The default
  configuration is for hosts.

### Slot framing and the slot boundary

- `start_slot()` resets the front end. Nothing else is kept: decodes have
  been handed to the caller, and the call table is the caller's.
- `skip(n)` advances over a gap; the missing samples count as zeros and
  are reported. `rows_filled()` reports progress.
- Decoding a partial slot is allowed: missing rows are absent.
- Non-finite input samples are replaced by 0.0 and counted in the report.
- One workspace serves every slot. While `decode` and `finish` run at a
  slot boundary, the caller buffers the next slot's first samples in a
  short FIFO and feeds them afterwards. The FIFO length equals the decode
  time.
- Later stages (subtraction, block detection) need signal phase, which
  the spectrogram does not keep. They will read caller-held audio, either
  re-fed after subtraction or passed per candidate. That input gets a
  separate, additive entry point; `decode_candidate` keeps its
  signature.

### API shape

- **12 kHz only.** `feed` (`f32` and `i16`) accepts any block size, and
  the result does not depend on the block sizes.
- **Workspace.** The spectrogram slice and the front-end buffers are
  borrowed from the caller (a `static` on a microcontroller, a `Vec` on a
  host). The `Decoder` value itself is small. Constants name the
  recommended capacities for hosts (200 candidates, 128 decodes) and small
  targets (200, 64): `CANDIDATES`, `HOST_DECODES`, `SMALL_DECODES`.
  `CANDIDATES` sizes the candidate buffer for the largest `candidates`
  value a preset or a caller's `with_candidates` uses and the
  measurements cover, not for the default: the presets use fewer
  (`HOST` 100, `SMALL` 75), and a compile-time check keeps every preset
  within it.
- **Truncation** is reported in a `DecodeReport`, never silent: candidates
  found, kept, decoded and rejected; truncation; sanitised and skipped
  samples.
- **Decode entries** hold the payload, message type, frequency (tone 0),
  time offset (from the nominal 0.5 s start), SNR (2500 Hz), sync score,
  candidate index, hard-error count and message-passing rounds, but no
  text.
- **`finish`** renders text through a callback into caller storage, using
  the caller's `CallHashes`. That table persists across slots and may be
  shared with transmitting. A valid payload of a type this crate cannot
  unpack is still reported, with its payload and the unpack error.
- **`finish_payloads`** returns payloads without unpacking, for callers
  that unpack elsewhere.
- **Errors:** new variants for configuration and buffer-size mistakes, in
  the non-exhaustive `Error`.
- **No threads in the core.** For parallel callers there is a split API:
  `find_candidates`; then `decode_candidate(&self, index, &mut
  CandidateScratch)`, with a shared read-only workspace and one scratch
  per thread; then the results pushed into a `DecodeList` in index order
  (out of order is an error); then `finish`.
- **Configuration** (`DecodeConfig`): the check-node rule, the round
  limit, the soft-bit scale, the minimum sync score and the candidate
  capacity. Both check-node rules are configuration, not build options:
  sum-product is the host default (`DecodeConfig::HOST`) and normalised
  min-sum, about a third of the cost per round, the provisional choice
  for small targets (`DecodeConfig::SMALL`) until instruction counts
  confirm it. Both are covered by the decode golden hash. `HOST` keeps
  100 candidates and `SMALL` 75 (2026-10-27; both 200 before). On every paired synthetic set (10–40 signals per slot) they
  decoded the same messages as 200 within noise: one sweep message of
  about 59 000 transmitted lost by each preset (found only by candidate
  171 or 151), none gained, no false decode, and no shift of the 50%
  point (95% bootstrap interval +0.000 to +0.000 dB on both seed
  blocks). 75 was the lowest value swept; on the host it lost a
  fresh-block message at candidate rank 78 and left a one-signal margin
  in the external comparison on 40-signal slots, so the host keeps
  more. The external comparison at 100 lost nothing. Time per crowded
  slot, one thread, AMD Ryzen Threadripper 3970X, loop-aligned build,
  median of five interleaved runs: host 66.4 → 40.4 ms (200 → 100
  candidates), small 44.8 → 26.3 ms (200 → 75). Busier bands than the
  measured 40 signals per slot should raise `candidates` with
  `with_candidates`; recovering crowded-slot decodes is later
  subtraction work.
- **Building blocks** (sync search, soft bits, belief propagation) are
  crate-private; a measurement feature exposes them to benches only.
- **Cost counts.** `CandidateScratch::last_rounds()` (and
  `BpScratch::rounds()`) report the message-passing rounds the last
  candidate ran, whatever its result: a deliberate, read-only public
  addition for callers that measure or budget decoding cost, free on the
  decode path.

### Determinism contract for decodes

1. **Candidate order.** Candidates are ordered by integer sync score
   (descending), then row, then base bin. All are integers, so there are
   no floating-point ties.
2. **Local-maximum suppression.** A 3 × 3 suppression in time and
   frequency runs before the top-K selection, with a fixed tie rule.
   - A grid point is kept if its score is ≥ every neighbour that comes
     later in (row, bin) order and > every neighbour that comes earlier,
     so a plateau of equal scores keeps its first point.
   - Neighbours outside the grid (before the first or after the last time
     position, below or above the band) impose no condition.
3. **`decode_candidate`.** It fully re-initialises its scratch, includes
   refinement and the SNR estimate, and is a pure function of the
   workspace and the candidate. It writes no hash table.
4. **Merge, then `finish`.** `DecodeList::push` (or `merge`) takes
   results in candidate-index order — out of order, or a decode carrying
   another index, is an error — and applies all-zero rejection (counted),
   duplicate removal (the lowest index is kept) and truncation to
   capacity (counted). `finish` then unpacks the list in order on one
   thread, following the sender-only hash memory recorded above.
5. **`decode()`** is defined as `find_candidates`, then `decode_candidate`
   for each candidate in order, each pushed into the list; it excludes
   `finish`, which the caller runs afterwards. A test checks the two paths
   are identical.
6. **Condition.** For the same input samples (bit patterns), configuration
   and starting call-table state, the output — order, payloads, text,
   frequency, time offset, SNR — is identical on every platform with
   IEEE-754 binary32 round-to-nearest arithmetic and without flush-to-zero
   or denormals-are-zero, for any feed block sizes and any thread count.
   A golden hash of the decode output for seeded synthetic slots is
   asserted in CI on Linux and Windows, and in an `ubuntu-24.04-arm`
   (aarch64) job for this crate.

### False-decode guards

The all-zero codeword passes the CRC (zero initial value) and every
parity check, so a carrier or other narrow-band interference can produce
it. It is rejected. Each decode records its hard-error count and
message-passing rounds, as inputs to later false-decode gating.

### Provenance per stage

| Stage | Source |
|---|---|
| Spectrogram | Short-time Fourier transform with a Hann window (standard); 2× oversampling in time and frequency, as consulted in `ft8_lib`. |
| FFT | Cooley–Tukey mixed radix (Cooley and Tukey, 1965; Singleton, 1969); own code. |
| Numeric helpers | `log2` from the IEEE exponent and an atanh series of the reduced mantissa; `exp2` from the IEEE exponent and a Taylor series of 2^f; standard constructions, own code, checked against `libm`. |
| Sync | Costas arrays (Costas, 1984), with the pattern and positions from QEX §4. The score and local-maximum suppression are this crate's own; `ft8_lib`'s scoring was consulted. |
| Soft bits | The max-log metric of QEX §6 with single-symbol detection (N = 1). Variance normalisation was consulted in `ft8_lib`; this crate scales by the mean magnitude instead (no square root). |
| LDPC decoding | Belief propagation (Gallager, 1962; MacKay, 1999), or normalised min-sum (Chen and Fossorier, 2002), over the crate's parity-check table. `ft8_lib`'s decoder was consulted. |
| Refinement | Sub-grid time and frequency offsets from a parabola through the sync scores of each candidate's grid neighbours (standard peak interpolation); soft bits from power interpolated bilinearly at the refined position. This crate's own. |
| SNR | The 2500 Hz definition of QEX §6. This crate's estimator: decoded-tone power at the refined position against a local noise reference — each side's lower octile level over bins 25–100 Hz from the signal, over its rows, corrected for the exponential distribution, then the mean of the two sides — so a sloping receiver passband and nearby signals bias it little; calibrated on synthetic slots in white and in shaped noise. |
| Later | Ordered-statistics decoding (Fossorier and Lin, 1995; QEX §6 cites Wu and Hadjicostis, 2007); a-priori decoding (QEX §6; it raises the false-decode rate, so it will be gated and measured); subtraction (QEX §6). |

WSJT-X source is not used for any stage.

### Tests

**CI tests need no WSJT-X tool.** Slots are synthesized with this crate's
encoder and seeded Gaussian noise:

- stage tests, including the FFT against a reference DFT and the tables
  against `libm`;
- an SNR sweep with pinned decode-rate floors;
- thousands of noise-only slots, including carrier-plus-noise slots, with
  zero decodes (a release-build job of its own);
- non-overlapping and overlapping (10–30 Hz apart) signals, including a
  strong signal next to weak ones;
- time-offset and frequency ranges, including the partial-sync edges;
- partial and late input, and decoding before the slot ends;
- block-size and thread-count invariance, workspace reuse and two
  alternating workspaces, and repeatable text with a seeded call table;
- the SNR estimate on white, shaped and steep-edged noise and beside a
  strong neighbour;
- the golden decode output, for both configurations, on Linux, Windows
  and aarch64.

The noise in these tests comes from `libm` (pure Rust), so the inputs are
the same bits on every platform.

No recorded audio is stored in the repository.

**External comparison.** Comparison with an external reference decoder on
synthetic slots, across SNR, time offset, frequency, crowding and fading,
runs in an external benchmark harness outside CI.

### Decode command output (format version 0)

`cat-ft8-decode` reads a 12 kHz mono 16-bit WAV (the first 15 s; a
shorter file is a partial slot) and prints one JSON object per decode:
`{"freq": Hz, "dt": s, "snr": dB, "message": "...", "candidate": n,
"hard_errors": n, "rounds": n, "score": n}`.

- `freq` is the tone 0 frequency.
- `dt` is the start relative to the nominal 0.5 s.
- `snr` is the SNR in 2500 Hz against the local noise.

By default only unpacked decodes are printed. `--config host|small`
selects the configuration: host is 100–3100 Hz, sum-product and 128
decodes; small is 200–2900 Hz, min-sum and 64 decodes.

- `--raw` adds payloads that did not unpack, as `"payload"` (hex),
  `"type"`, `"error"` and `"unpacked": false`.
- `--profile` adds one `{"profile": {...}}` line: the format version,
  the configuration with its band and decode capacity, stage times in
  keys ending `_seconds`, memory in keys ending `_bytes` (with
  `peak_bytes`), and every decode report count.

The format is documented in the crate and stays at version 0 until a
release. The JSON is written by hand, with string escaping, so
`serde_json` stays a dev-dependency (tests parse the output with it).

### Time budgets

The time budget is the profile's total from the first `feed` of a slot to
the return of `finish`, single-threaded, excluding file I/O and one-time
start-up. Results name the host CPU.

| Where | Budget |
|---|---|
| Host | Mean ≤ 100 ms per crowded (40-signal) synthetic slot, one thread on an otherwise idle desktop-class x86_64 core; `feed` ≤ 1% of real time. |
| Cortex-M33-class part (≈ 150 MHz, single-precision FPU) | `feed` ≤ 25% of real time per 80 ms hop; decode within the slot-boundary FIFO's length. |

Measured (2026-10-27) with an external benchmark on synthetic slots
(the comparison with a reference decoder is kept outside this
repository), host configuration, one thread on an AMD Ryzen Threadripper
3970X:

- decode rate: the 50% point on the synthetic tuning set at −19.18 dB,
  with no false decodes; −19.30 dB on a held-out synthetic set; about 63%
  of signals decoded in crowded 40-signal slots;
- cost before the optimisation passes: about 0.10 s of CPU per slot,
  including process start. Crowded slots took 94 ms on average, 105 ms
  at the 95th percentile and 114 ms at most, per process including
  start-up, with sixteen decodes running in parallel on a 32-core part;
  noise-only slots took 95–97 ms, since all 200 candidates then run the
  full 30 rounds. These are an upper bound for the idle single-process
  figure the budget names, which was not measured separately; the
  budget had no margin;
- cost after optimisation pass 1 (vectorised belief-propagation check
  updates, results bit-identical), same conditions: crowded slots about
  72 ms on average (77 ms at the 95th percentile), the sweep set 75 ms.
  Measured one process at a time, the decoder's own stages total about
  69 ms per crowded slot (belief propagation 46 ms, feed 15 ms). The
  host budget now has a margin of roughly a quarter;
- cost after the candidate-count reduction (`HOST` 100 candidates and `SMALL` 75 instead
  of 200, results within noise of the 200-candidate decoder): about
  40.4 ms per crowded slot for the host configuration and 26.3 ms for
  the small one, one process at a time (median of five runs); the
  external benchmark's CPU per slot roughly halved (about 0.10 s to
  0.05 s including process start). Early stopping of failing
  candidates was measured and rejected;
- working memory 236 232 B on the host, as in the table above.

The repository's own evidence is the decode bench
(`examples/decode_bench.rs`) and the pinned floors and golden hashes of
`tests/decode.rs`.

On a 256 KiB part, the small configuration is used with a 1 s i16 FIFO
(24 000 B, caller-owned) and a 1 s decode budget. Operation-count
estimates put the microcontroller well inside its budget:
the FFT is about 4% of real time; sync search (≈ 961 base bins × 63 time
positions × 21 Costas symbols × a few operations ≈ 5 million) and about
140 candidates' belief propagation take under 1 s together.

- Instruction counts come from QEMU (an MPS2 Cortex-M33 model), which
  gives instruction counts, not timing.
- Microcontroller timing is claimed only once measured on a development
  board.

### Embedded link check

From the first decoder step on, `embedded-check` calls each new stage.
In its final form it feeds a synthesized slot, in blocks, into the
decoder from a static workspace with no allocator. It fails on any
unresolved symbol or any `f64` helper, and reports flash, `.bss` and
stack. It links three images: the small configuration (200–2900 Hz,
min-sum, 64 decodes), the host configuration (100–3100 Hz, sum-product,
128 decodes) and the encoder alone, as a baseline for the decoder's
size. The check-node rule is a run-time field, so both rules are linked
in either decoder image.

### Waveform API growth

Subtraction will need a reference signal at a fractional frequency
(already possible) and a sub-sample start, with the per-sample phase and
envelope that `fill_phase` already exposes. New entry points are
additive. Existing outputs and golden hashes do not change; new outputs
get new golden hashes.

## Amendment (2026-10-27, revised): subtraction and further passes

Status: **Accepted** (2026-10-28: implemented, measured, and the
acceptance gates under "Measured" below passed in this repository's
bench; API revised after review the same day). The
step plan is in `planning/cat_ft8/task_plan.md` (Phase 4); the
measurements it rests on are in `planning/cat_ft8/findings.md` ("Misses
by cause", "Subtraction ceiling", "Bench split, and no-candidate misses
told apart", "Wider crowded set, measured", "Subtracting one signal
(S2)", "Further passes (S3)").

### Scope

Subtracting decoded signals from the slot's audio and decoding the
residual again, for a configured number of passes (1 to 3). Pass 1 is
the single-pass decoder unchanged. Out of scope here: ordered-statistics
and a-priori decoding, multi-symbol block detection, subtraction on
small targets.

### Evidence

The reference is a same-configuration oracle: the slot rebuilt without
the messages decoded so far (true waveforms, same noise) and decoded
again with the same configuration. It is a reference, not a bound: a
real further pass decodes different input.

- On the in-repo crowded set (10, 20 and 40 messages per slot,
  −16…+6 dB, two seed blocks) the host decodes 69.1% of the messages in
  one pass, 91.0–91.6% with one oracle pass and 96.5–97.0% with two.
  Every message decodes alone in its slot, so the ceiling (decoded by
  the single pass, alone or an oracle pass) is 100% on this set.
- On a wider crowded set (10, 20, 30 and 40 messages per slot,
  −22…+5 dB, its own seeds) the host decodes 62.3–62.5% in one pass,
  81.8–82.0% with one oracle pass and 86.2–86.4% with two; the ceiling
  is 89.3–89.8%.
- Of pass 1's misses on the crowded set (host, main block), about 80%
  have a non-converging candidate on them, 8% have no sync peak on them
  and 11% have a peak that the candidate limit dropped; CRC failures are
  negligible.
- With `decode::subtract` and the bench's own pass loop (no
  `DecodeConfig::passes` yet), one further pass recovers 96.6% of the
  oracle's +1 gain on the crowded set and 93.0% on the wider set (two
  further passes: 94.8% and 89.5%), and 94.9% on a set whose signals
  fade, drift and start between samples; a subtracted payload is decoded
  again about once in 10 000 subtractions after the first further pass,
  and no further pass made a false decode. One signal in white noise is
  suppressed to its amplitude estimate's noise (−37.8 dB at +10 dB SNR).

### API (additive)

- The **residual** is caller-owned and always the full slot from slot
  sample 0, with the skipped region (the first `skip` samples) zero; the
  caller feeds `&audio[skip..]`.
- `decode::subtract(audio: &mut [f32], decode: &Decode, skip: usize,
  config: &SubtractConfig) -> Result<Subtraction, Error>` (as built in
  the subtraction step; the band argument first proposed was not
  needed, the skipped length was): a free function that subtracts one
  decoded signal from the residual in place, neither reading nor writing
  the skipped region. Fine time (whole samples) and frequency (offset
  and linear drift) estimate, then a least-squares complex amplitude per
  segment (`SubtractConfig::segment`, default one symbol), linear
  between segment centres, then the scaled unit reference from
  `fill_phase`. The returned `Subtraction` carries the estimates and an
  estimate of the signal left. Bounded stack storage (4 536 B of
  arrays; about 7.3 KB of frames on thumbv8m); no new workspace buffer;
  no decoder state.
- Each later pass uses the existing calls: `start_slot()`, `skip(skip)`,
  `feed(&audio[skip..])`, `find_candidates`, `decode_candidate`, into
  the same `DecodeList`. There is no separate pass-start call.
- `DecodeList::next_pass()` only resets the candidate-index order check.
  The caller records the list's length to know where each pass begins.
  Payloads are de-duplicated across passes by the existing duplicate
  rule (the earliest is kept).
- `DecodeConfig::passes` (validated 1..=3; 1 = the single-pass decoder),
  `DecodeConfig::later_candidates` (one candidate count for every later
  pass; `Decoder::find_later_candidates` searches with it) and
  `DecodeConfig::subtract` (the subtraction settings). A pass that adds
  no decode ends the loop (deterministic), and so does a pass that
  leaves the list full (a further pass could only list again what it
  truncated). The candidate buffer needs
  `DecodeConfig::candidate_capacity()` entries, the larger of the two
  counts whatever the pass count; `DecodeConfig::max_decodes()` is the
  most a slot can list (200 for `HOST`, above `HOST_DECODES` = 128,
  which truncates beyond the validated 40 signals). After measured
  acceptance `HOST` decodes in three passes with 50 later candidates and
  3 840-sample segments; `SMALL` stays at one pass. `Decoder::decode`
  always runs one pass.
- `Decoder::decode_passes(&mut self, audio: &mut [f32], skip, scratch,
  list)` runs `start_slot`, `skip` and `feed` itself for every pass,
  pass 1 included, and subtracts each pass's decodes before the next. It
  overwrites the caller's buffer with the residual (the slot minus the
  decodes of every pass but the last); with one pass the buffer is
  unchanged.
- `Decoder::decode_further_passes(audio, skip, scratch, list)` runs
  passes 2 and on after a pass 1 run separately (fed block by block as
  the audio arrives, decoded with `decode` or the split API);
  `decode_passes` is pass 1 followed by it, so the pass loop exists
  once. `feed_i16` takes a sample as `x / 32 768` exactly, so a pass 1
  fed as `i16` blocks followed by further passes over those values as
  `f32` is bit-identical to `decode_passes` (tested). A later borrowed
  argument for per-slot hints (a-priori decoding) can be added to it.
- `report()` after several passes: `Decoder::report` keeps its meaning
  (the last search, the last input fed, the list's counters), so after
  several passes it describes the last pass. `decode_passes` returns a
  `PassesReport`: its `DecodeReport` has one meaning, the whole slot —
  search, list and rejection counts summed over every pass run, input
  counters from the slot's audio as pass 1 fed it — beside the passes
  run, the subtractions made (and failed, not expected) and why no
  further pass ran (`PassesEnd`). Per-pass counts are in `PassReport`.
- Budgets: `DecodeConfig::max_subtractions` (default none) starts a
  further pass only if its subtractions fit under the cap, so a capped
  slot's output is a reproducible prefix of the uncapped one's; the
  staged callback returns `ControlFlow`, and a `Break` stops the decode
  after the current candidate pass or subtraction (a wall-clock safety
  net, reported as `PassesEnd::Stopped`).
- `Decoder::decode_passes_staged` is the same with a callback for each
  step of each pass (`PassEvent`, `PassStep`: one `Subtract` step per
  decode subtracted) and each pass's counts (`PassReport`: where the
  pass began in the list, decodes subtracted before it, duplicates of
  earlier passes' payloads, belief-propagation rounds, and the pass's
  own search and list counts), for profiling. `PassStep` and `Stage` are
  a profiling surface that grows; consumers match on them in profiling
  code only.
- `decode_candidate` keeps its signature. The decode command's lines
  gain a `"pass"` field (format version 0, additive), so `pass` and
  `candidate` identify a decode; the profile adds keys. The pass count is
  reachable from the command (`--config host,passes=N`, replacing the
  draft's "no flag").

### Determinism

Subtraction runs in a fixed order — pass, then list index — on one
thread, so the split/threaded API remains bit-identical to one thread.
With one pass every existing output and golden hash is unchanged;
multi-pass setups get their own golden pins, asserted on every CI
target.

### Waveform API growth

This replaces the expectation above of a sub-sample start in `Synth`.
The subtraction reference is built at unit amplitude from `fill_phase`
at a whole-sample start and scaled outside `Synth` by the estimated
complex amplitude; `Synth` gets no amplitude parameter. A sub-sample
start is added to `Synth`, additively, only if the subtraction step
measures timing residue above −30 dB (half a sample of start error
gives a phase error between tones of at most 2π × 43.75 Hz × 1/24 000 s
≈ 0.011 rad, about −39 dB). With a zero fraction its outputs would be
bit-identical and the existing golden waveform hashes would not change.
Measured in the subtraction step: the residue of a start between
samples is −57.7 dB at a half-sample start and −53.3 dB at worst, so
`Synth` gets no sub-sample start.

### Memory and cost

The residual is caller-owned: 180 000 `f32` samples (720 000 B), beside
the core's working memory, which does not grow. Multi-pass decoding
gives up block-by-block streaming: pass 1 can be fed as audio arrives,
but every later pass needs the whole slot, so subtraction is a host
feature (an `i16` residual is still 360 000 B, beyond the 256 KiB
class).

There is one time budget per slot, not one per pass:

| Decoding | Budget | Slot mix |
|---|---|---|
| Single pass (host) | Mean ≤ 100 ms per slot, as above | The crowded set's 40-signal slots, as in the time budgets above. |
| Multi-pass (host) | Worst slot ≤ 250 ms in total; the mean recorded | Every 40-signal slot of the crowded set's main block (all 200): for each slot the median across at least five interleaved runs, one thread; the budget applies to the largest of those medians. |

Each pass also has a deterministic bound: its candidates × 30 rounds of
belief propagation, plus one `feed` of the slot, one sync search and the
subtraction of the previous pass's decodes. Per-pass costs are recorded.

### Measured (2026-10-28, this repository's bench)

Settings swept on the main blocks (segment 1 920, 2 880, 3 840 samples
× later candidates 20–200 × two or three passes), confirmed on the
fresh seeds: `HOST` = three passes, 50 later candidates, 3 840-sample
segments (fewer later candidates decode the same messages as 200; longer
segments recover more). Against the single pass (paired, per message):

| set (main / fresh) | single | three passes | gains − losses | share of the oracle's +1 / +2 gain |
|---|---|---|---|---|
| crowded | 69.1% / 69.1% | 96.0% / 96.6% | 3 767 − 0 / 3 853 − 0 | 98.9% / 98.2%; 99.1% / 98.6% |
| wide | 62.5% / 62.3% | 85.0% / 85.2% | 4 496 − 0 / 4 572 − 0 | 96.9% / 94.8%; 96.7% / 94.8% |
| fading | 63.3% / 62.7% | 85.7% / 85.5% | 3 137 − 0 / 3 189 − 0 | 97.4% / 95.3%; 97.0% / 95.0% |

The wider set's ceiling is 89.3% / 89.8%. No false decode in any pass
on any set (crowded, sweep, edges, wide and fading, both blocks; empty);
sweep and edges unchanged (b = c = 0, the sweep's 50% point and its
whole bootstrap interval unmoved); the CRC-based expected false decodes,
summed over passes, at most 2.8 × 10⁻⁶ per slot, within passes × the
single pass's rate on every set. Cost on the measuring host (one thread):
the worst 40-signal crowded slot 213.7 ms (budget 250 ms), mean 197.5 ms;
single pass mean 38.9 ms.

### False decodes

A further pass is a new set of candidates, so its expected false-decode
rate from the CRC (CRC failures × 2⁻¹⁴ per slot) adds to pass 1's; the
acceptance bar is at most passes × the single-pass rate. Measured false
decodes must be zero per pass on the crowded, sweep and edge sets (both
seed blocks) and on a fading/drift set, and zero on the empty set and in
the bulk run; the empty set alone cannot test later passes, since with
nothing decoded there is nothing to subtract. Residue of an imperfect
subtraction is a new false-decode and duplicate risk; a later pass
re-decoding a subtracted payload is counted as a failed subtraction.
