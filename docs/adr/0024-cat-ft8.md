# ADR 0024 — `cat-ft8`: FT8 from the published protocol, with a `no_std` core

Status: Accepted (2026-10-26)

## Context

FT8 is the most used digital mode on the HF bands. Applications built on
this library want to send it, and later to decode it, beside the CAT
control, audio and Morse support they already get here.

It belongs in this repository for the same reason `cat-morse` does
([ADR 0021](0021-cat-morse.md)): almost all of it is radio-independent.
The message formats, error correction, tones and waveform are the same for
every radio, so putting them in one application would mean every other
application copies them. Like `cat-morse`, the crate keys nothing and
opens no sound card; it turns text into samples (and, later, samples into
text).

The reference implementation, WSJT-X, is licensed under the GPLv3. This
library is Apache-2.0. The protocol itself is published: S. Franke, B.
Somerville and J. Taylor, "The FT4 and FT8 Communication Protocols", QEX,
July/August 2020. `ft8_lib` (Kārlis Goba, MIT) is an independent
implementation that interoperates with WSJT-X.

FT8 decoding is CPU-heavy. A `no_std`, allocation-free core lets
applications run it on small embedded targets as well as on hosts.

## Decision

**A new workspace crate, `cat-ft8`, implements FT8 from the published
protocol description.** This first release is the transmit half: message
packing (and unpacking, which tests and the future decoder need), CRC-14,
LDPC (174,91), tone mapping and GFSK waveform synthesis. Decoding follows
in later releases in the same crate, each with its own plan and an
amendment to this ADR.

### Scope rules

1. **No radio.** No keying, no CAT and no dependency on `cat-framework`,
   any `cat-transport-*` or any radio crate.
2. **No device audio.** It writes `f32` PCM at 12 000 Hz into the caller's
   buffers (the `std` feature can also write a WAV file). Playback belongs
   to the application.
3. **`no_std` core, no dependencies.** The crate is `#![no_std]` in every
   build and has no dependencies at all. The core allocates nothing
   (fixed-size arrays and caller-provided buffers) and starts no threads.
   All floating-point work is `f32` `+ − ×`: there is no `f64` and no
   transcendental function at run time, because the pulse shape and sine
   are tables in static data. CI proves this on every change for
   `thumbv8m.main-none-eabihf`: the library builds and lints for that
   target, and `cat-ft8/embedded-check` links a `#![no_main]` program
   with **no allocator** and fails on any unresolved symbol or any `f64`
   soft-float helper (`__aeabi_d*`, `__*df*`) in the image. The program
   calls `encode` (pack, CRC, LDPC, tones) and `unpack`, and every public
   entry point that does floating-point work — `Placement::slot`,
   `synthesize` (at a negative start), `Synth::new`, `fill`, `mix`, `skip`,
   `fill_phase`, `sin_turns` and `cos_turns` — because only reachable code
   is linked and so checked. The remaining public functions are
   integer-only. A new floating-point entry point must be added to it. Injecting one `f64`
   operation into `synthesize` makes the check fail.
4. **Features.** `std` (default) adds `std::error::Error`, WAV output and
   the `cat-ft8-encode` binary. `profile` (default-off) builds the
   `encode_bench` example, which reports CPU time per stage, the memory
   account and a heap-allocation count; it does not change the library.
   CI builds both, tests the host build without `std`, and builds the docs
   with warnings as errors in both configurations (ADR 0014 §5).
5. **No unsafe code** in the library (`#![forbid(unsafe_code)]`).
6. **Errors** are one hand-written `Error` enum, `#[non_exhaustive]` so
   the decoder can add variants. `thiserror` is not used: the workspace's
   `thiserror` 1.x needs `std`. `thiserror` 2 supports `no_std` and was
   considered; a dependency for one `Display` impl was not worth it.

### Provenance

- **Implemented from the QEX 2020 paper** (Tables 1–3 and 7, §3–5,
  Appendix A). WSJT-X source code is not read, copied, ported or
  translated.
- **WSJT-X tools are black-box test oracles only.** The encoder vectors in
  `cat-ft8/tests/data/` were generated from WSJT-X 3.0.0-rc1 `ft8sim`
  output (its printed payload bits, channel symbols and its own unpack of
  each message), and WSJT-X's `jt9` was used to confirm by hand that the
  synthesized audio decodes. Neither is linked, shipped or needed to build
  or test this crate. Where the paper is silent or WSJT-X differs from it,
  this crate follows what the oracle does (listed below), so both put the
  same bits on the air.
- **`ft8_lib` (MIT) was consulted** — its CRC, message packing, encoder
  (LDPC encoding and tone mapping) and waveform code — and is credited in
  `cat-ft8/NOTICE`. Copied from it: the
  LDPC generator and parity-check matrices (the paper defines them by
  reference to files it does not print). Followed from it: the waveform's
  extension of the first and last tone beyond the transmission, which the
  paper does not specify. Taken from it: the callsign-hash multiplier
  (47 055 833 459) and the order of the 38-character callsign alphabet,
  which the paper defers to reference programs it does not print; the
  free-text alphabet the paper prints matches. The Rust for CRC, packing,
  LDPC encoding, tone mapping and synthesis was written from the paper; no
  `ft8_lib` function was translated. The tables and the
  hash multiplier originate in WSJT-X; they are interoperability constants
  of the protocol and are used here as facts.

### The determinism promise

Packing, CRC, LDPC and tone mapping are integer-only. The waveform uses
only IEEE-754 `f32` `+ − ×` (Rust never fuses them into FMA), a 32-bit
fixed-point phase accumulator, and two tables in static data: the GFSK
pulse (QEX eq. 3) and a quarter-wave sine, read by the top phase bits and
linearly interpolated with an integer-derived fraction. Both tables are
generated with `libm` and checked bit-for-bit by a test, so `libm` is a
dev-dependency only (pinned exactly). Given IEEE-754 binary32 arithmetic
with round-to-nearest — every target with SSE2 or a hardware
single-precision FPU, and soft-float targets, but not x87-only targets
such as i586, which round through extended precision — **the same
symbols, frequency, amplitude and position give bit-identical samples on
every platform**, whether rendered in one call or in blocks. (`mix` into a
zeroed buffer equals `fill` except in the sign of zero.) Tests pin FNV-1a hashes of synthesized waveforms
and full slots; CI runs them on Linux and Windows. A deliberate change to
the waveform changes the hashes in the same commit.

### Recorded design choices

- **Message types.** Packed and unpacked: 0.0 free text, 0.1 DXpedition,
  0.5 telemetry, 1 standard, 2 EU VHF `/P`, 4 nonstandard call, 5 EU VHF
  contest. Returned as `Error::Unsupported(type)`: 0.3/0.4 ARRL Field Day
  and 3 ARRL RTTY Roundup, which need the ARRL/RAC section and
  state/province tables whose order is part of the protocol; they are left
  for a later release rather than guessed. Their text shapes are recognised
  so they are reported as unsupported instead of being sent as free text.
  The unassigned types (0.2, 0.6, 0.7, 6, 7) unpack as
  `Error::InvalidPayload`, as do field values no message defines (for
  example a standard-call value `pack` never produces).
- **Text rules follow WSJT-X 3.0**, checked against `ft8sim`:
  - type 1/2 signal reports run from −50 to +50 dB (the paper says −30 to
    +99; WSJT-X carries −31…−50 in otherwise unused values and shows
    anything above +50 as `dd − 101`);
  - `RR73` is sent as the locator RR73 (g15 = 32 373), not the reserved
    value the paper lists; both unpack to `RR73`;
  - free text shorter than 13 characters is right-aligned (leading
    spaces);
  - any single word of 1–18 hexadecimal digits is telemetry (0.5);
  - in a type 4 `CQ` message the ignored `h12` field holds the hash of the
    call itself;
  - a hashed `<call>` goes in a type 1 message beside a standard call
    without suffix, or beside another hashed call when neither contains
    `/`; beside a nonstandard or `/R`/`/P` call, or with a compound (`/`)
    call in both brackets, the message is type 4;
  - type 5: both calls bracketed (12- and 22-bit hashes), report 52–59
    and serial 0–2047 written as six digits, a 6-character locator.
- **Where WSJT-X loses information, this crate refuses.** WSJT-X
  truncates free text to 13 characters, drops a report it cannot fit into
  type 4, drops the prefix of an unbracketed compound call (`PJ4/K1ABC
  W9XYZ` is sent as `K1ABC W9XYZ`), wraps reports above +50, clamps a type
  5 serial above 2047, and drops the `+` of `+1` (sending telemetry 1).
  For the first five, `pack` returns an error; `+1` is sent as free text.
  Some compound-call shapes WSJT-X cannot pack still fit as free text and
  are sent that way, losslessly. Nonstandard calls are never hashed
  implicitly: the text must bracket one call.
- **Callsign hashes** are resolved through a `CallHashes` trait;
  `CallTable<N>` is a fixed-capacity table that keeps the `N` most
  recently heard calls (re-hearing refreshes a call). Parsing has no side
  effects: a successful `pack` offers the message's full calls once (the
  text is the operator's own); a failed one offers nothing. `unpack`
  remembers what WSJT-X 3.0 remembers when it decodes, checked black-box
  with `jt9`: only the sending station — the second call of a type 1/2
  message, the full call of a type 4 message when it is the sender, nothing
  from DXpedition or type 5 — exactly as written, so after `K1ABC/P` a hash
  of `K1ABC` alone does not resolve. It resolves every hash in the message
  first and remembers only after the whole payload has decoded. A miss shows `<...>`, as WSJT-X does. 10- and 12-bit hashes
  collide in practice; the protocol cannot tell such calls apart.
- **Unpacking writes to the hash table**, so a decoder that wants
  reproducible output must unpack its decodes in a fixed order on one
  thread, and only payloads that passed CRC and LDPC. The decoder's plan
  records how it does this.
- **CRC-14**: polynomial 0x6757, initial value zero, over the 77 payload
  bits zero-extended to 82 (QEX §3).
- **Waveform**: Gaussian-smoothed frequency pulse with BT = 2 (QEX eq. 3),
  tone spacing 6.25 Hz, 1920 samples per symbol at 12 kHz, three
  overlapping pulses per sample, a raised-cosine ramp over the first and
  last T/8 (20 ms, QEX §5), first and last tone extended beyond the
  transmission. A slot places the signal at 0.5 s + dt. `Synth` streams
  the waveform into caller blocks of any size (`fill`, `mix`), so a small
  target never needs the 607 KB waveform or 720 KB slot in memory, and
  exposes each sample's carrier phase and envelope (`fill_phase`) from the
  same generator. **The waveform API will grow** when the decoder needs a
  reference signal for subtracting decoded signals; transmit and
  subtraction will share this generator.

## Verification

- `cargo test -p cat-ft8`: per-stage unit tests (CRC; every LDPC basis
  codeword satisfies the parity checks and every single-bit flip breaks
  one; Costas positions and property; Gray map against QEX Table 3; the
  static tables against `libm`; sine accuracy; pulse normalisation,
  frequency, ramps; block rendering equal to one call; golden hashes);
  seeded property tests (round trips of every supported type; a random
  payload fuzz in which `unpack` never panics and, with the call table
  seeded with the calls behind each hash, every supported type — hashed
  types 1, 4, 5 and 0.1 included — repacks to the same bits or has a
  named non-canonical reason); and three black-box vector
  files. Every payload in them maps to `ft8sim`'s symbols; every supported
  message packs to `ft8sim`'s bits and unpacks to its text. Unsupported
  types, oracle failures and the documented deviations are counted, never
  skipped silently.
- `cat-ft8/embedded-check/check.sh`: the bare-metal link check above; with
  `--stack` it also prints per-function stack frames.
- Audio checked by hand with WSJT-X's `jt9` (not part of the test suite,
  which must not need WSJT-X).

## Consequences

- Applications get an FT8 transmit path with no GPL code in it, usable on
  hosts and microcontrollers alike, with no dependencies.
- The decoder will extend this crate under the same rules: `no_std` core,
  memory reserved up front by the caller, `f32`, no threads in the core.
- Field Day and RTTY Roundup messages need their lookup tables before they
  can be supported.
- Behaviour that follows WSJT-X rather than the paper is listed above, so
  a later WSJT-X change is a deliberate update to the vectors, not a
  surprise.
